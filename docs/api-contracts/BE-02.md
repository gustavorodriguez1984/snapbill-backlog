## Regla transversal (no es un endpoint nuevo)

Todas las operaciones que **mueven inventario** validan el período fiscal/mes operativo a partir de la **fecha del documento** (`InvoiceDate`, `ReceiptDate`). **No** se persiste `TenantPeriodId` en tablas transaccionales.

### Timezone

Año y mes se extraen de `documentDate.UtcDateTime` (calendario UTC, alineado con BE-01).

---

## Comandos afectados

| Comando | Campo fecha | Cuándo valida |
|---------|-------------|---------------|
| `POST /api/v1/invoices` | `invoiceDate` | Solo si la factura incluye líneas de **producto** (mueve stock) |
| `POST /api/v1/purchase-receipts` | `receiptDate` | Recepción **directa** (sin OC vinculada → impacto inmediato en stock) |
| `PATCH /api/v1/purchase-receipts/{id}/receive` | `receiptDate` del documento existente | Al confirmar recepción (pasa a `Recepcionada`) |

Recepciones vinculadas a OC en estado `Aprobada` **no** validan en el create (sin movimiento de stock); la validación ocurre en **receive**.

---

## Error común — período cerrado o inexistente

**HTTP 400** — `application/problem+json`

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Validation",
  "status": 400,
  "detail": "Operación rechazada: El período para la fecha del documento se encuentra cerrado o no configurado.",
  "errorCode": "PeriodClosedOrNotConfigured"
}
```

| errorCode | Cuándo |
|-----------|--------|
| `PeriodClosedOrNotConfigured` | No hay `TenantPeriod` para el año/mes UTC de la fecha **o** `isClosed = true` |

---

## Verificación manual

1. Tenant con período actual abierto (BE-01).
2. `POST /api/v1/invoices` con producto y `invoiceDate` en mes abierto → **201**.
3. Cerrar mes en SSMS (`TenantPeriods.IsClosed = 1`) → repetir → **400** `PeriodClosedOrNotConfigured`.
4. Recepción directa con `receiptDate` en mes cerrado → **400**.
